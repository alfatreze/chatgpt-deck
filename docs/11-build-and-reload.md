# Build and reload procedure

This procedure is intentionally incomplete until the Phase 0 SDK/runtime discovery finishes. It is a guardrail against a common false positive: a C# package may build successfully but fail to load in Logi Plugin Service.

## Build gate

Before adding a production action, verify all of the following on the reference host:

1. The selected C# SDK/tool and target framework are compatible with the installed Logi Plugin Service and reference surface. The generated `net8.0` template was the historical failure; the project now builds and loads with `net10.0` to satisfy `PluginApi`’s `System.Runtime 10.0` dependency.
2. `dotnet --info` matches the target framework selected by the plugin SDK.
3. A development `.link` points to the locally built plugin in the documented Plugin Service plug-in directory.
4. The host reloads the plugin without a restart loop.
5. One action is visible, can be assigned, and writes a recognizable log line when pressed.
6. The exact log location and reload command are recorded in [the environment baseline](10-development-environment.md).

## Confirmed official bootstrap (macOS)

After .NET 10 has been installed and `dotnet --info` succeeds, run these commands from the repository root:

```zsh
dotnet tool install --global LogiPluginTool
logiplugintool generate CodexDeck
cd CodexDeckPlugin
dotnet build
```

The generator should create the project and the build should write a development link at:

```text
~/Library/Application Support/Logi/LogiPluginService/Plugins/CodexDeckPlugin.link
```

The first manual verification is to open Loupedeck, expose the installed plugin in the Action Panel, assign its sample action, press it once, and read the plugin-specific log below. Exact file names are generated by the tool and must be captured after the first run.

```text
~/Library/Application Support/Logi/LogiPluginService/Logs/plugin_logs/
```

`dotnet watch build` from the generated project’s `src` directory is an optional later hot-reload path—not a substitute for validating a real reload and physical press. The initial physical press path is now verified.

## Required development loop

1. Change one focused unit of source or configuration.
2. Build with the recorded SDK/runtime command.
3. Update the development link through a project-owned build target or documented command.
4. Trigger a plugin reload.
5. Read the plugin log immediately.
6. Test one physical action and one failure path.

Never commit `bin`, `obj`, local SDK/tool caches, development links, generated packages, or logs. The project `.gitignore` is the baseline; update it when the selected SDK introduces additional generated paths.

## Evidence record

The build/reload procedure is proven with Logi Plugin Service `6.4.1.3246`, .NET SDK `10.0.401`, and `net10.0`. P0-01a additionally has three verified physical presses and action-specific log lines; remaining hardware work is limited to documenting the exact device model and visual rendering observations.
